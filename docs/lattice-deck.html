The domain

Pre-clinical toxicology — regulatory study analysis

What varies across studies
Species: rat, dog, primate, rabbit — different biology, different expected findings, different N (rat: 10-20/group, dog: 3-5)

14 SEND domains: BW, LB, MI, MA, OM, CL, FW, CV, EG, VS, DS, BG, RE, IS — body weight to immunology

Routes: oral, IV, IM, subcutaneous — different PK, different target organs
Why it's hard for automation
1,032 unique endpoints across 15 organ systems — liver ALT and brain histopath need different statistics

Small N: dog/primate studies have 3-5 animals per group. LOO is bimodal, HCD has 25-35% false alarm rates. The value is honest uncertainty, not p-values

Cross-domain signals: liver weight + ALT + hepatocyte hypertrophy = hepatotoxicity syndrome. No single endpoint tells the story

Species biology, compound pharmacology, statistical method selection, severity grading, recovery assessment, historical controls — all interact. Every rule has species exceptions.

The starting point

Markdown prompt files. Tell the LLM what to do, it does it. 

/lattice:research {topic}     LLM reads prompt, does research, writes output
/lattice:implement {spec}     LLM reads spec, writes code
/lattice:review               LLM reviews its own code, commits

Works for: simple features, one-shot tasks, known territory.

Then the project got bigger. And everything started breaking.

Act 1: Single-task quality

Can the LLM do one task well?

Self-review is worthless

The LLM reviews code it just wrote. The rationale for every decision is in its context window. It literally cannot see its own blind spots.
Fix: Independent context. Peer review, architect review, and decision audit each run in a separate agent with no access to the main conversation.
Three independent reviewers
peer-review — scientific correctness
architect-reviewer — overengineering
decision-auditor — merit-driven choices
Protocol
Two review rounds, hard cap.
No Round 3 — that's always bikeshedding.
Unresolved → escalate to human with evidence.

LLMs can review. They can't review themselves. Context is the enemy of objectivity.

Research doesn't compound

After 20+ research files, the LLM researches something we already know, or contradicts a prior finding. Each session starts fresh — no memory of the corpus. Today: 134 research files, 777-line REGISTRY tracking cross-dependencies.
Fix: /lattice:distill — corpus-level reasoning across ALL accumulated research.
Reads REGISTRY.md (stream status, dependencies, invariants at risk).
Every claim tagged: decided > peer-reviewed > unreviewed > inferred 
### loo-discount                             # REGISTRY entry
- Status: decided (implemented)
- Touches subsystems: S02 (gLower), S10 (signal formula)
- Affects: signal-scoring, outlier-sentinel, noael-determination
- Invariants at risk: X1, X2, X3 (CRITICAL: must not mutate ep.gLower)
- Validation: 48/49 signals unchanged. 86 stable, 49 fragile, 13 maximally fragile.

Research without synthesis is trivia collection. The value is in connections between findings.

Bug fixes are shallow

LLM fixes a bug in module A. The exact same pattern exists in modules B, C, D. Nobody checks. Same bug surfaces two days later.
Fix: /ops:bug-stress — mandatory post-fix QC.
Classify (10 pattern families) → search entire codebase → fix ALL instances → add tests.
/ops:bug captures during QA → BUG-SWEEP.md. Patterns logged to bug-patterns.md.
3+ bugs in the same family → extract a pattern test suite.

A bug is never just one bug. It's a pattern with N instances. Fix the class, not the instance.

Act 2: Process discipline

Individual tasks work. Can it follow a multi-step workflow?

The human is the bottleneck

Each cycle requires the human to invoke ~8 skills in the right order, make routing decisions, remember where they left off across sessions. The workflow knowledge lives in the human's head.
Fix: Phase-scoped orchestrators that auto-detect entry points and run autonomously. 
/lattice:cycle {topic}               auto-detect phase, dispatch to:
  /lattice:research-cycle             7 steps, 2 peer review rounds
  /lattice:blueprint-cycle            7 steps, architect gate + 2 plan reviews
  /lattice:build-cycle                4 steps, E2E gate + quality review

State persisted to .lattice/cycle-state/{topic}.yaml (47 active topics).
Cross-session resume: read state file, skip completed checkpoints, continue.

The human's role shifts from "invoke the next step" to "make the hard decisions."

Prose rules don't work

CLAUDE.md says "run validation before committing." The LLM skips it ~40% of the time. Not maliciously — it gets focused and forgets. Rules written as prose are suggestions, not constraints.
Prose ruleEnforcementArtifact
"Review before committing"Pre-commit hook BLOCKSreview-gate.json (single-use)
"Check validation scores"Pre-commit hook BLOCKSvalidation-baseline.json
"Don't repeat failed approaches"Agents read log at startdecisions.log (424 entries)
"Tag commits with Topic:"PreToolUse hook WARNScommit-topics.tsv
"Don't skip peer review"Orchestrator re-launchesQuality gate checks output

If the machine can skip it, the machine will skip it. Make constraints mechanical.

Separate orchestration from behavior

Skills = what each node does (markdown). DAGs = when, dependencies, routing (YAML). 

nodes:
  research:
    type: skill
    skill: lattice/research
    checkpoint: { state_key: research.1, phase: research }

  peer-review-r1:
    type: skill
    skill: lattice/peer-review
    depends_on: [research]
    context: fresh                    # separate agent -- no context leak

  evaluate:
    type: gate
    depends_on: [peer-review-r1]
    evaluate:
      - condition: "...contains('FLAWED')"
        route: escalate               # human decision needed
      - condition: default
        route: incorporate             # auto-accept, continue

7 workflow DAGs • 5 node types: bash skill gate approval parallel • Same YAML, different executors (CLI today, Slack/CI later)

Act 3: Portfolio management

Individual workflows work. Can it manage 47 topics at once?

Parallel topics conflict silently

Topic A and Topic B both modify the scoring engine (subsystem S10). Topic A's blueprint was validated before Topic B's research. Neither knows about the other. Both build. One overwrites the other.
Fix: Coherence engine. Reads all 47 topic state files, maps subsystems from system-manifest.md (25 subsystems), detects conflicts before any topic advances.
Conflict typeWhat
Subsystem overlapTwo active topics modify the same subsystem
Stale blueprintBlueprint validated before newer relevant research
Unresolved cascadeScience flag in topic A propagates to topic B
Prerequisite violationTopic B depends on unfinished topic A

Single-topic quality is table stakes. Portfolio-level awareness prevents integration disasters.

State files drift from reality

An agent crashes without updating state. Another commits without a trailer. Someone edits a YAML by hand. The coherence engine reads stale data and makes wrong decisions.
Fix: Truth lives in git, not in YAML. Every commit carries a Topic: trailer. Reconciliation greps git log, compares against state files, auto-corrects drift. lattice status runs reconciliation first, always. 
feat: continuous HCD percentile in D4 confidence dimension

Topic: hcd-informed-z-scoring
Phase: complete
Coverage: HCD/LB, interpretation engine

Derived state > stored state. If you can reconstruct it from commits, do that.

Act 4: Towards unattended

The workflow runs. The portfolio is managed.
What's still missing before it can run alone?

"It builds" is not "it works"

Build passes, tests pass, review passes. But a scoring formula "simplification" changed 15% of signal detection results. Nobody tested the actual analytical output.
Fix: Two complementary gates.
E2E testing gate
Run suites on base state AND changed state.
Compare results. Three auto-detected modes:
branch • uncommitted • last-commit
Validation ratchet
Compares validation-baseline.json
against 16 ground truth study cards
in docs/validation/references/

Together they catch "correct code, wrong science." Degradation doesn't mean rollback — it means the change needs research.

What works

1. Independent context for review.
Single most impactful change. Catches issues self-review misses every time.

2. Mechanical enforcement over prose rules.
Hooks, single-use gate files, locks with stale recovery. Non-bypassable.

3. YAML DAGs for orchestration.
Versionable, diffable, portable across executors.

4. Portfolio-level awareness.
Cross-topic coherence catches what single-topic quality misses.

5. Git as source of truth for state.
Commit trailers + reconciliation. Derived > stored.

6. Two-round peer review with a hard cap.
Round 3 is always bikeshedding. Escalate after 2.

What doesn't work

1. LLM self-assessment of any kind.
Not for review, quality, or rule compliance. Separate agent or mechanical check.

2. Natural language constraints.
"You should always..." gets ignored under load. Convert to hooks or gates.

3. Stored state without reconciliation.
Any file the LLM maintains will drift. Derive from git or reconcile constantly.

4. One-shot bug fixes.
The LLM fixes the symptom, not the pattern. Must search for same pattern everywhere.

5. Cost estimation without measurement.
Token counts vary 10x for "similar" tasks. Parse real data, don't guess.

The meta-lesson

The framework isn't 50 files of
"tell the LLM what to do."

It's 50 files of
"prevent the LLM from doing
what it naturally does wrong."

Every capability exists because we observed a failure and built a constraint.
The framework is a catalog of LLM failure modes with mechanical fixes.
