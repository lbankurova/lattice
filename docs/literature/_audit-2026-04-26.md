### Common patterns of error

1. **"Waterfall" framing is lazy and self-flattering.** Both `gsd.md` and `obra-superpowers.md` reject the source as "waterfall" and contrast against lattice's "build first, spec after". This misrepresents BOTH the source AND lattice. Lattice's `/lattice:research-cycle -> /lattice:blueprint-cycle -> /lattice:build-cycle` (per `WORKFLOW.md` lines 47-142) is itself a sequential phase pipeline — research produces validated research, blueprint produces a validated build plan, build produces committed code. The honest contrast is **flexibility of entry point and ceremony weight**, not waterfall vs. anti-waterfall. Spike (`commands/lattice/spike.md`) is explicitly framed as "a spike is a time-boxed exploration… If it works, the code stays and a spec is generated afterward" — i.e. an EXCEPTION mode, not the modus operandi.

2. **Convergent invention claims are unverified.** `gsd.md` claims "Spike came from `obra/superpowers`". Verified against `gh api repos/obra/superpowers/git/trees/main?recursive=1` — there is NO spike skill in superpowers. The 14 superpowers skills are: brainstorming, dispatching-parallel-agents, executing-plans, finishing-a-development-branch, receiving-code-review, requesting-code-review, subagent-driven-development, systematic-debugging, test-driven-development, using-git-worktrees, using-superpowers, verification-before-completion, writing-plans, writing-skills. So both `obra-superpowers.md` (claims spike was borrowed from superpowers) AND `gsd.md` (claims convergent invention from superpowers) are factually wrong.

3. **Rejection rationales conflate "we don't have it yet" with "merit-based rejection".** `gsd.md` rejects UAT/HITL verification as "over-ceremony for the current scale" — but for a 1-non-dev-plus-Claude shop, *some* HITL gating is critical (and lattice does have it via review-gate.json + ESCALATION.md, which the note doesn't mention). `gsd.md` rejects wave-based parallel execution as "coordination complexity without obvious win for a one-developer-plus-Claude shop" — Claude Code natively supports parallel sub-agents (lattice's own `commands/lattice/review.md` runs three reviewers in parallel), so the rejection is unfounded.

4. **Misreads of CLAUDE.md rule 8.** `ahrens-smart-notes.md` invokes rule 8 to reject atomization. Rule 8 (verified at `C:/pg/pcc/CLAUDE.md` line 65) is about "creating new top-level directories under `docs/` or anywhere in the repo root" — explicitly NOT about file count or atomization within an existing folder. Atomizing knowledge entries under `docs/_internal/knowledge/` does not violate rule 8.

5. **Audience-scope rejection of widely-applicable patterns.** `ahrens-smart-notes.md` rejects "Slip-box as a writing-only tool. Ahrens frames it for academic publishing." The framing is true at the source (verified — Ahrens names "students, academics, nonfiction writers" as audience at line 414, and "software engineer / programmer / developer" appears 0 times as audience), but the rejection ignores that Zettelkasten is widely adapted to engineering knowledge work (Andy Matuschak's evergreen notes, Maggie Appleton's gardens). The rejection should be framed as "we adapt the workflow shape, the audience scoping doesn't transfer cleanly" not "Ahrens frames it for publishing, therefore reject".
