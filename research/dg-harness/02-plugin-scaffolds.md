## 2. What `grok create` produces

### 2.1 Source

- CLI command: `tools/bin/commands/create.ts` (222 lines).
- Templates: `tools/package-template/` (the directory copied into a new package) and `tools/entity-template/` (per-entity snippets).

### 2.3 What `grok create my-plugin` produces, end to end

After running `grok create my-plugin --ts`:

```
my-plugin/
├── .gitignore                  # JetBrains / VSCode / dist / node_modules / src/**/*.js
├── .npmignore                  # Like .gitignore, dist NOT excluded
├── CHANGELOG.md                # ## 0.0.1 (<today>)
├── README.md                   # Single-line stub
├── detectors.js                # Empty <Name>PackageDetectors class
├── package.json                # 30 lines, references datagrok-api ^1.26.0
├── package.png                 # Default icon
├── tsconfig.json               # Strict + decorators + sourceMap
├── webpack.config.js           # ts-variant; externals list; FuncGeneratorPlugin
└── src/
    ├── package.ts              # Renamed from package.js; same content
    ├── package.g.ts            # EMPTY at create time; regenerated on first webpack build
    └── package-test.ts         # Test entry with `test()` + `initAutoTests()`
```

The directory-creation script is `createDirectoryContents` (`create.ts:25-123`). Placeholder substitution runs on every text file: `#{PACKAGE_NAME}`, `#{PACKAGE_DETECTORS_NAME}` (camelCased package name), `#{PACKAGE_NAME_LOWERCASE}`, `#{PACKAGE_NAME_LOWERCASE_WORD}` (hyphens stripped), `#{CURRENT_DATE}` (ISO date), `#{PACKAGE_NAMESPACE}`, `#{GROK_HOST_ALIAS}`, `#{GROK_HOST}` (`create.ts:41-50`).

**Side effect:** `grok create` runs `npm install` after writing files (`create.ts:199-202`), so the post-create state includes `node_modules/` and `package-lock.json`. The "ready to develop" state is reached without further commands; `grok publish` works immediately (assuming `~/.grok/config.yaml` is set up).

**Config side effect:** `~/.grok/config.yaml` is auto-created from `tools/config-template.yaml` if missing (`create.ts:136-138`). Validation runs via `validateConf` (`tools/bin/validators/config-validator.ts`), which checks for `default` field, `servers` object, URLs, and dev keys.

### 2.4 What the empty plugin can do at the moment after `grok create`

- Builds: `npm run build` chains `grok api && grok check --soft && webpack` and produces `dist/package.js` + `dist/package-test.js` + sourcemaps.
- Publishes: `npm run debug-my-plugin` (or `grok publish`) uploads to the default server in debug mode.
- Tests: `grok test` runs the `package-test.ts` harness against a local Datagrok instance; the empty package has no actual tests.
- Exposes one function: `info()` (visible in the Datagrok function browser).

**It does NOT contain:** any viewer, any detector body, any connection, any query, any script, any custom view, any ESLint config (unless `--eslint`), any tests beyond the runner itself (unless `--test`).

### 3.3 Entry-point patterns observed

| Pattern | Where found | Shape |
|---|---|---|
| **Bare JSDoc, free function** | Most older packages, `Chembl`, `ApiSamples` | `//name:` + `//meta.role:` + `//input:` + `//output:` directly above an `export function`. Example: `tools/entity-template/function.ts:1-9` |
| **`PackageFunctions` static class with `@grok.decorators.*`** | `Charts`, `Tutorials` | Static methods on a `PackageFunctions` class, decorated. Webpack plugin extracts and emits `package.g.ts` with the JSDoc form. Example: `packages/Charts/src/package.ts:20-99` |
| **Mixed (free function + class with decorators)** | `Chem` | Both forms coexist; widgets and panels use free-function JSDoc; viewer demos use decorators |
| **Detectors as a separate class in `detectors.js`** | All packages with custom sem-types | `class <Name>PackageDetectors extends DG.Package { ... methods with //meta.role: semTypeDetector ... }`. Example: `packages/Chem/detectors.js:4-60` |
| **Tests via `package-test.ts` + `tests/` subdir** | All packages with tests | `package-test.ts` is the runner shell; actual tests in `tests/test-*.ts` files imported into the runner. Example: `tools/entity-template/test.ts` (cat 'Examples', 3 sample tests with `expect`/`throw`/`skipReason`) |

### 3.4 The minimal-viable pattern

What every plugin needs at minimum (verified across all 5 sampled):

```
my-plugin/
├── package.json                # name, version, datagrok-api dep, build script
├── webpack.config.js           # externals list, FuncGeneratorPlugin
├── tsconfig.json               # strict + experimentalDecorators (TS only)
├── CHANGELOG.md                # X.Y.Z (date) format
├── README.md
├── detectors.js                # empty class is fine; just the file
└── src/
    ├── package.ts              # imports grok/ui/DG, exports _package
    ├── package.g.ts            # webpack-emitted (commit it)
    └── (one or more entity files: viewer, function, app, panel, ...)
```

That's 7 source files + 2 dotfiles to ship a usable plugin.

### 3.5 The fully-featured pattern

Adds, in roughly the order acquired:

- `src/package-test.ts` + `src/tests/` (when adding tests via `grok add tests`)
- `connections/<name>.json` + `queries/<name>.sql` (when adding DB)
- `scripts/<name>.{py,r,js,jl,m}` (when adding scripts; per `tools/bin/utils/utils.ts` `scriptLangExtMap`)
- `css/<name>.css` (when adding custom styling — imported via `import '../css/<name>.css'` in `package.ts`)
- `images/`, `icons/`, `files/` (data; `files/` is mounted at `System:AppData/<PackageName>/`, see `C:/datagrok/public/CLAUDE.md:272-274`)
- `src/viewers/<viewer-name>/` (when viewers grow; convention seen in Charts and Chem)
- `src/widgets/`, `src/panels/`, `src/analysis/`, `src/utils/`, `src/rendering/` (Chem-style sub-domain organization)
- `src/package-api.ts` (generated by `grok api` — wraps DB queries and scripts as TS callable functions)
- `dockerfiles/`, `environments/` (when the plugin needs server-side compute, e.g., Chem's RDKit-Docker pipeline)

**Build progression:** `grok api && grok check --soft && webpack` is the universal "build" recipe (verified: present in `Charts/package.json:40`, `Chem/package.json` (likely; pattern matches), `tools/package-template/package.json:21`). The order matters: `grok api` must run before `grok check` (which validates the generated `package-api.ts`), which must run before `webpack` (which regenerates `package.g.ts` via `FuncGeneratorPlugin`).

## 4. Agent-callable helpers — what would they be?

For each operation an agent would perform on a plugin, this section names: (a) what files change, (b) the diff shape, (c) the input schema a skill would need, (d) the validation step.

**This section enumerates and characterizes; it does not propose new skills.** Skill design is the orchestrator's synthesis task.

### 4.1 "Add a viewer to this package"

**Today's manual recipe:** `grok add viewer <Name>`.

**Source:** `tools/bin/commands/add.ts:244-267`.

**Files changed:**
- New: `src/<name-kebab>.ts` (the viewer class file). Generated from `tools/entity-template/viewer-class.ts` (43 lines).
- Modified: `src/package.ts` — content prepended with `import {<Name>} from './<name-kebab>';\n`. **Note:** the `add` command `prepends` — it does not insert at a specific anchor. Subsequent imports will accumulate at the top.
- Modified (regenerated on next build): `src/package.g.ts`.

**Diff shape (sketch):**

```diff
+ src/awesome-viewer.ts (new file, 43 lines from tools/entity-template/viewer-class.ts with #{NAME} → AwesomeViewer)
  src/package.ts:
+ import {AwesomeViewer} from './awesome-viewer';
  // existing content unchanged
```

The viewer template is decorator-based (`tools/entity-template/viewer-class.ts:5-9`):

```typescript
@grok.decorators.viewer({
  name: '#{NAME}',
  description: 'Creates #{NAME} viewer'
})
export class #{NAME} extends DG.JsViewer {
  constructor() { super(); }
  init() {}
  onPropertyChanged(property: DG.Property | null) { super.onPropertyChanged(property); this.render(); }
  detach() {}
  onTableAttached() {
    this.subs.push(this.dataFrame!.selection.onChanged.subscribe((_) => this.render()));
    this.subs.push(this.dataFrame!.filter.onChanged.subscribe((_) => this.render()));
    this.render();
  }
  render() { /* ... */ }
}
```

**Skill input schema (what the agent would receive):**

```yaml
package_path: string                    # absolute path
viewer_name: string                     # PascalCase, must end with 'Viewer' per add.ts:250-251
description: string                     # optional, defaults to 'Creates <Name> viewer'
icon_path: string                       # optional, relative to package root
toolbox: boolean                        # optional, default false
trellisable: boolean                    # optional, default false
viewer_path: string                     # optional, e.g., 'Add | JS Viewers | <PackageName> | <Name>'
```

**Skill output (files the agent commits):**

- `src/<viewer-name-kebab>.ts` (new)
- `src/package.ts` (modified, one import line)
- `src/package.g.ts` (regenerated by webpack — agent runs `npm run build` to refresh)

**Validation step:** `grok check --soft` (`tools/package-template/package.json:21`'s `build` script chain). The check that fires is `checkFuncSignatures` (see 01-platform-jsapi §3.2 row 7) against the `viewer` role signature `viewer(): Viewer`. If the class doesn't extend `JsViewer`, the build still passes (the type system accepts it; only runtime would fail), so the harness needs a stricter check than the platform ships — a candidate for §3.5 of the platform doc (custom `grokChecks`).

### 4.2 "Register a function"

**Today's manual recipe:** `grok add function <Name>` (or `grok add function panel <Name>` / `grok add function init <Name>`).

**Source:** `tools/bin/commands/add.ts:138-163`.

**Files changed:**
- Modified: `src/package.ts` (or `.js`) — appended with the entity template content. **Note:** `add` `appends` for `function`, `app`, `view` (`add.ts:160`: `fs.appendFileSync(packageEntry, insertName(name, func));`).

**Templates:**
- `tools/entity-template/function.ts` (default): bare function with `//name:`, `//input:`, `//output:`.
- `tools/entity-template/panel.ts` (`tag === 'panel'`): adds `//meta.role: panel`, `//description:`, `//condition: true`, returns a `DG.Widget`.
- `tools/entity-template/init.js` (`tag === 'init'`): empty async function with `//meta.role: init`.

**Skill input schema:**

```yaml
package_path: string
function_name: string                   # camelCase per validateName (add.ts:42-46)
role: enum('function', 'panel', 'init', 'autostart', 'app')
description: string                     # optional
inputs: list of {type, name, options}   # each becomes //input: type name {options}
output: {type, name}                    # becomes //output: type name
meta: dict                              # becomes //meta.<key>: <value>
```

**Validation:** `grok check` runs `checkFuncSignatures` and matches against `functionRoles[]` (see 01-platform-jsapi §2.9). For each known role, the input/output types must match the canonical signature. **Failure modes the validator catches:** wrong number of inputs, type mismatch, forbidden parameter names (`function`, `class`, `export`), unknown header tag, `meta.cache` value not in allowlist, `meta.invalidateOn` without `meta.cache`, invalid cron.

### 4.3 "Add a script (Python/R/JS scripts)"

**Today's manual recipe:** `grok add script <lang> <Name>` (or `grok add script panel <lang> <Name>` for context-panel scripts).

**Source:** `tools/bin/commands/add.ts:69-119`.

**Files changed:**
- New: `scripts/<name>.<ext>` (extension from `tools/bin/utils/utils.ts:scriptLangExtMap` — `javascript: js`, `nodejs: js`, `python: py`, `r: r`, `julia: jl`, `octave: m`).
- The script template (from `tools/script-template/<lang>.<ext>`) is copied with `#{NAME}` substitution.

**Template shape (per language; sampled — javascript example):**

The `script-template/` dir has one file per language with the canonical header:

```javascript
//name: #{NAME}
//description: Sample #{NAME} script
//tags: demo
//input: dataframe table
//output: dataframe result
```

For `panel` tag, the comment `//meta.role: panel` is inserted right after the `//name:` line via `nameLineRe` (`add.ts:108-114`).

**Skill input schema:**

```yaml
package_path: string
script_name: string
language: enum('javascript', 'nodejs', 'python', 'r', 'julia', 'octave')
panel: boolean                          # if true, adds //meta.role: panel
description: string
inputs: list                            # script-language-specific input types
output: type
```

**Validation:** `checkFuncSignatures` runs against the script's header annotations, parsed with the language-specific comment regex (`tools/bin/utils/utils.ts:201-206` — `py: ^#\s*...`, `ts/js: ^//\s*...`, `sql: ^--\s*...`). **Per-language gotcha:** Python uses `#`, R uses `#`, SQL uses `--`. The tooling supports them all; the harness just needs to pass the right `lang` flag.

### 4.4 "Wire a semantic-type detector"

**Today's manual recipe:** `grok add detector <SemType>`.

**Source:** `tools/bin/commands/add.ts:268-291`.

**Files changed:**
- Created (if absent): `detectors.js` — derived from `tools/package-template/detectors.js` with the package-name placeholder substituted.
- Modified: `detectors.js` — a new method inserted *inside* the `<Name>PackageDetectors extends DG.Package { ... }` class body (`add.ts:281-282`: `idx = contents.search(/(?<=PackageDetectors extends DG.Package\s*{\s*(\r\n|\r|\n)).*/);`).

**Template (`tools/entity-template/sem-type-detector.js`):**

```javascript
//meta.role: semTypeDetector
//input: column col
//output: string semType
detect#{PACKAGE_DETECTORS_NAME}(col) {
  if (col.name.startsWith('#{NAME_PREFIX}')) {
    col.semType = '#{NAME}';
    return col.semType;
  }
  return null;
}
```

**Skill input schema:**

```yaml
package_path: string
sem_type_name: string                   # the value returned and assigned to col.semType
detection_strategy: enum('column-name-prefix', 'column-name-regex', 'value-regex', 'sample-categories', 'custom')
prefix_or_regex: string                 # used by column-name strategies
sample_size: number                     # used by sample-categories strategy
custom_body: string                     # raw JS body for custom strategies
```

**Validation:** `grok check` validates the detector method's input/output against the `semTypeDetector` role signature `semTypeDetector(col: Column): string` (`js-api/src/const.ts:471-475`). Detectors live in `detectors.js` which is uploaded *separately* from the main bundle (per `help/develop/how-to/functions/define-semantic-type-detectors.md:51-53`), so a detector with a webpack-only dependency will silently fail to load — a class of bug the platform's check does not catch.

### 4.5 "Add a property descriptor to a viewer"

**No `grok add` command exists for this.** Today the manual recipe is to edit the viewer class directly, calling `this.string('propName', defaultValue, options)` / `this.bool(...)` / `this.int(...)` etc. inside the viewer constructor. These are inherited from `JsViewer` via `Viewer.props` (`ObjectPropertyBag`, `js-api/src/viewer.ts:399-405`).

**Files changed:**
- Modified: `src/<viewer-kebab>.ts` — a new line inserted in the viewer class constructor (or `init()` method).

**Diff shape:**

```diff
  export class AwesomeViewer extends DG.JsViewer {
    constructor() {
      super();
+     this.maxBars = this.int('maxBars', 100, {min: 10, max: 1000, category: 'Display'});
    }
    ...
+   maxBars: number;  // declare the type
  }
```

**Skill input schema:**

```yaml
package_path: string
viewer_class_name: string               # used to locate the file
property_name: string                   # camelCase
property_type: enum('string','int','float','bool','dateTime','column','column_list','dataframe')
default_value: any
options: dict                           # min, max, choices, category, fieldName, semType, etc.
```

**Validation:** none mechanical today. `JsViewer` properties are runtime-registered; `grok check` does not introspect viewer class bodies. The harness would need a TS-AST-aware audit (parsing the viewer file with `@typescript-eslint/typescript-estree` like `FuncGeneratorPlugin` does) to produce a property inventory — that's a candidate custom check.

### 4.6 Cross-cutting validation gate

Across §4.1-4.5, the universal post-edit validation step is the same three-stage pipeline:

1. `grok api` (regenerates `src/package-api.ts` from queries/scripts; required if the change touches `queries/`, `scripts/`, or any DB/connection file).
2. `grok check --soft` (the validator from `tools/bin/commands/check.ts`; see 01-platform-jsapi §3 for the 9-check list).
3. `webpack` (regenerates `src/package.g.ts` via `FuncGeneratorPlugin`).

These three are chained in the canonical `npm run build` script (`tools/package-template/package.json:21`). For agent harnessing, the validation step on every helper must run all three — single-command `npm run build` from the package directory is sufficient.

## 6. Open questions for thread discussion

1. **`@grok.decorators.*` vs JSDoc-form parity.** The decorator surface (23 decorators, `js-api/src/decorators/functions.ts`) and the JSDoc-comment grammar (~20 directives + open-ended `meta.*`, parsed in `tools/bin/commands/check.ts:709-805`) carry overlapping but not identical option sets. The decorator's TypeScript option types include fields like `condition`, `topMenu`, `editor`, `cache`, `cache.invalidateOn`, `helpUrl`, `connection`, `sidebar`, plus a `Meta` interface with 50+ fields (`decorators/functions.ts:117-166`). Some of these are not in `headerTags` (`tools/bin/utils/utils.ts:194-199`). Question: which is canonical when they diverge? The answer determines whether agent helpers should generate decorator-form (richer types) or JSDoc-form (older but `grok check`-validated).

2. **The `meta.json` non-existence.** None of the 5 sampled packages carries a `meta.json`. The prompt asked about it; the public repo doesn't have it. Is this a planned-but-not-yet-shipped surface, or a misnomer for `package.g.ts`? If it's the former, agent helpers built today against `package.g.ts` would need a future migration.

3. **`grok add` mutation scoping.** `grok add function` *appends* to `package.ts`; `grok add view` *prepends* one import then appends; `grok add detector` *inserts inside* the class body. Three different mutation strategies. For agents, this is a contract: the helper must know which strategy applies. Is there any plan to unify (e.g., always insert at named anchors / `// EXPORTS_BELOW` / `// IMPORTS_ABOVE`)? If not, agent helpers will have to reproduce all three logics.

4. **Scaffold completeness for an *empty* test workflow.** `grok create` produces `package-test.ts` but no actual `tests/` directory; the user has to run `grok add tests` separately (`add.ts:292-340`). Should the harness's project scaffold ship with `tests/` pre-created (so the empty plugin is "tested" from minute zero), or follow the existing two-step pattern? This is a small policy call but determines whether agent-driven plugin development starts in a passing-tests state or not.

5. **Where does `~/.grok/config.yaml` live for an agent?** The `grok` CLI reads `~/.grok/config.yaml` (`tools/CLAUDE.md:94-106`). For an agent running in CI / sandbox / Docker, the home-dir is non-obvious and varies (`/root`, `/home/node`, etc.). The `grok claude` Docker entrypoint auto-creates one (`tools/CLAUDE.md:211`), but an agent run *outside* `grok claude` has no such convention. For the harness work, this is a deployment-shape question — should the harness ship a config-bootstrap script, or rely on the user having already configured the CLI?
